# 2026-10-23: making `fly babysit` run Stage 1 end to end

Researcher instruction (2026-10-23): the goal is a babysit command that trains the Fly end to end; "you are going to have to make your own decisions". This entry records the decisions, mistakes and pivots made while closing the remaining gaps. It does not claim a scientific result.

## Decisions (researcher delegated these)

1. **Stage 1 evaluator authority.** The working-tree evaluator (SHA256 `54573da2...` before this work) is treated as authoritative. Check-run pins (`ff6f...` in v7, `6c65...` in v2–v5) are receipts of what those finished runs tested; nothing live depended on them. New runs get fresh pins.
2. **Stage 1 data: explicitly synthetic micro-tasks.** Lichess roots supply provenance and the focal capture identity (the puzzle's first solution move: actor/target squares and piece types). Each task is a ≤6-piece FEN-rooted hypothetical position bound to the verified source history by an exact occupancy diff (`lichess-synthetic-task-position-v1`). Three templates: *absent* (relocate the defender between targets), *blocked* (move the slider to the other end of the target line), *pin* (move the enemy king off the pin line). Every board has exactly one certified successful action; pair success sets are disjoint, so no always-safe alternative can pass D5.
3. **Stratum labels.** Discovered design inconsistency: if every counterfactual pair flips the focal capture, each pair contains one open-defender board, giving 32 open boards in final rather than the frozen 16 per stratum; and a 6-piece pin cannot be kept on both boards of a pair. Resolution: each board's stratum is the classifier stratum of its predeclared focal probe. Pin families pair a pinned board with its open counterpart; blocked and absent families label each board by its successful probe. Final = 4 pin + 2 blocked + 2 absent families of 8 boards: exactly 16 per stratum, 32 reversing pairs. Pin families therefore mix two strata, departing from the design doc's "single-stratum family" plan; the code-enforced gates are unchanged.
4. **Receiver acceptance (G0) gates promotion, not training.** G0 has not passed. The matrix preflight previously refused any teaching without `receiverAccepted:true`. Now the audit must state the boolean, training may run, and the frozen D1–D8 gate still requires `receiverAccepted:true` for acceptance. Rationale: the core iteration rule favours feedback-enabled runs; Stage 1's own matched controls (D6/D9) test whether teaching causes learning. No G0 work was done.
5. **Stage 1 D7 is explicitly unavailable.** Frozen D7 for Stage 1 requires eight interference blocks of G0 contingency exposures through a reviewed receiver. The evaluator previously substituted end-of-acquisition validation (and read nonexistent `treatment.selectedChoices/lastChoices`, which would have thrown). Now it reports D7 as unavailable with a reason; the gate returns `unknown` but keeps D1–D6/D8/D9 metrics so a stopped campaign has a diagnosis.

## Defects found and fixed

- **Replicas were behaviourally identical.** `forward([0], stimulation)` multiplies the input projection by zero, so the per-replica model seed changed nothing; the encoder seed was shared. The brain factory now derives the public-cue projection seed from the replica seed.
- **The babysit could never launch a stage.** The Python preflight requires argv to end with `--cpu-duty 0.5`, but the matrix runner's strict `parseArgs` did not declare `cpu-duty`. The runner now accepts it and requires it to equal the registration's duty.
- **Stopped campaigns had no learning diagnosis.** The audit now carries one `diagnosis` line per replica (status, failed gates, unknown reasons, train/validation/final, probe and pair counts, control advantages).
- Unregistered stages now report their specific readiness reason instead of a generic missing-config message.

- Running the Python suite via `-m unittest` failed one self-command-line test (artefact of the launcher); running the file directly passes 32/32.

### Real-run defects (smoke revisions r1-r3; each preserved under its own run directory)

1. **r1:** `TypeError ... binarySha256`. The collector returns the *bound* Stockfish review, but the factory treated it as raw (read `engine`, re-bound it, and cached it). Underneath, the review was not ready: node-limited Stockfish searches usually end mid-iteration with only a bound, and the pinned exact-score rule (correctly) refuses bounds, so all-legal reviews almost never complete (an earlier probe measured 42/124 unavailable). Fixes: a registered `search:'depth'` mode (depth 10 and 14; completed iterations give exact scores; all 24 training panels ready in 67 s); the factory now reports the binder's reason, rebuilds and caches the raw review, and checks the identity. Fixture tests used a mocked analyzer and could not reveal either problem.
2. **r2:** `EPERM ... fsync`. Windows refuses to flush a read-only handle; the raw-log flush now opens `'r+'`. The babysit's interrupted record now includes the runner's stderr tail, so deterministic errors are visible instead of looking like resumable interruptions.
3. **r3 (direct runner debug):** `Teaching context mismatch`. The capture-retention feedback binder required the context to equal `{fen,pgn,task}`; synthetic contexts also carry `historyKind`/`parentSourceRecordSha256`. It now requires an exact board/history/task match and admits only the registered synthetic history kind.
- After these fixes the real Stage 1 learner ran feedback-enabled blocks (stage checkpoints 0 and 1 published). Measured cost: about 5 minutes per block at 0.5 duty, so the smoke (6 arms x 8 blocks) needs about 4 hours plus audit replay, and the full registered run (18 arms x 32 blocks) about 2 days of training plus replay.
- Known limit: a legal move that ends the game makes Stockfish answer `bestmove (none)`, which the collector rejects. No training board has such a move; future data should exclude them.

### Finding: the Stage 1 learner does not use the receiver G0 tests

Verified in code (no experiment): G0 constructs `RateTimingMemory` with the gamma2 map (`research/reports/plasticity-timing-candidate-2026-10-09/rate-timing-map.json`; PPL103->MBON12 groups only, explicit tau/step timing, full-frame `observeTrajectory`). The Stage 1 brain factory constructs plain `ReversalMemory` with the coarse dual-valence map (`research/reports/reversal-candidate-2026-10-05/mapping.json`; PAM02 and PPL103), and the coupled Stockfish brain requires both valence channels, so the gamma2 receiver is not a drop-in replacement. Consequence: even a future G0 pass would not certify the receiver that Stage 1 trains. `receiverAccepted` for Stage 1 therefore needs either a receiver test of this dual-valence `ReversalMemory` interface or a redesign of chess teaching around the G0 receiver. This is a researcher decision about the biological teaching interface; it was not changed here. The Stage 1 run still measures, with matched controls, whether this receiver supports consequence learning and transfer.

### Receipt analysis: taught boards are not being learned (2026-10-24, read-only)

Question: does the Fly improve even on the training boards it is taught repeatedly? Script (session scratchpad) read event-start rankings from receipts of full-r5 `r1:informative` (15 blocks so far). The rehearsal planner targeted the same two pin boards (`s1syn-train-f2-pin-p0a`, `-p1a`) in every block; on both the certified success `f7f6` stayed ranked 29/30 and 21/22 from block 1 to block 15, with an unchanged score gap (about 5.1-5.3e-3). Within one board: punishing the chosen wrong move (`h4e4`) lowered the correct move's MBON12 by about 0.0049 (0.02747 -> 0.02262), and rewarding the correct move raised it by about the same amount (0.02262 -> 0.02741 by the next visit), so the two lessons cancel. MBON01 for `f7f6` stayed at its initial 0.0273. Hypothesis (not yet tested): moves on the same board receive largely shared input, so "this move bad" and "that move good" act on the same memory and cancel. Consequence: the 32-block run is unlikely to reach D1 or D2 by more exposure alone. In G0 (toy cues, different receiver) acquisition did pass, so the plasticity itself is not inert.

### Measured: moves on the same board receive almost the same input (2026-10-24, read-only, no graph)

Step 1 of the agreed diagnosis. `public-lesson-frame-cue.mjs` turns a board+move into tokens (turn, castling, en passant, half/full-move counters, task, one token per piece, one per history ply, and a single `action:<uci>` token) and hashes each token onto one Kenyon cell. Measured on the 24 Stage 1 training boards with the r1 replica seed (script `cue-overlap.mjs` in the session scratchpad): 12.9 stimulated cells per cue; two moves on the same board share on average 85.6% of their cells (Jaccard; 3,953 pairs), identical for success-vs-failure pairs; typically 12 of 13 cells are shared. Different boards share 32.8%, mostly the six board-independent tokens. The only move-specific cell encodes the move string (for example `f7f6`), which means the same thing on every board regardless of chess meaning. This confirms the cancellation hypothesis at the input level: teaching "this move is bad" and "that move is good" acts mostly on the same 12 cells. Limit: measured at the stimulation level, not after full-graph dynamics.

## 2026-10-24: policy B and the action-centred input cue (revision 6)

**Decision (researcher):** policy B. Chess stages prove receiver causality with their own controls (D6/D8/D9); Stage 1 D7 is deferred to Stage 2. Implemented as `retentionDeferral` in the evaluator/gate (a new test checks that only the registered Stage 1 deferral is accepted and that it never rescues another gate) and `--receiver-policy stage-matched-controls-v1` in the data auditor; the v2 audits (`research/reports/lichess-stage1-synthetic-*-audit-v2.json`) pass all splits again (24/16/64 boards). The v1 audits are preserved.

**Second structural finding (code reading, not an experiment):** with `ReversalMemory`, failure (PPL103) depresses the active cue's KC->MBON12 gains, while success (PAM02) can only act through KC->MBON01, and only 84 of the 693 cue-pool KCs reach MBON01 (55 reach both). A v1 cue of about 13 cells therefore reaches about 1.6 success-teachable cells, so success feedback barely acted.

**Change:** new `public-action-relative-cue-v1` (`.codebase/src/chess-input/public-action-relative-cue.mjs`). Tokens are the task, the moving piece, what it captures (or none), its move vector, and every other piece's type/side relative to the landing square, oriented from the actor's side; position-only cues (Stockfish value channel) anchor on the last public move. Each token drives one KC in the MBON01 compartment and one in the MBON12 compartment. No attack, pin or outcome is computed. Offline, training rows only (`encoder-check.mjs`): same-board overlap 0.856 -> 0.183; a logistic token scorer (a representation diagnostic, not the Fly) fits 10/20 -> 20/20 training boards and scores 3/24 -> 11/24 on held-out training families. Limitation stated in advance: even that idealized scorer transfers to 11/24, below D2's 14/16 bar, so transfer is the expected next bottleneck.

**Also:** after a failed selection the evaluator now scores the training boards of every control arm at the informative arm's last checkpoint, so the stop diagnosis compares taught vs untaught learning. Tests 45/45 (+ 57/57 broader).

**Run:** `stage1-smoke-r6` (1 replica, 8 blocks, six arms) via `fly babysit --curriculum "python actions/curriculum-campaign-smoke-r6.json"`; log `runs/stage1-smoke-r6-babysit-1.log`. Question: does the Fly learn its taught boards, beyond matched controls?

### Revision 6, first four informative blocks (2026-10-24 10:35, receipts, read-only)

- **Within-event learning now works and is move-specific.** Examples (event-start rankings before and after one pulse on the same board): success taught on `g7f7` raised it from rank 7/21 to 1/21 (`f0-pin-p0b`); success on `c6b5` 3/26 -> 1/26; failure on `h4h5` lifted the correct `h4g5` from 19/21 to 7/21; a punished move dropped out of the top three. Under v1 these effects cancelled.
- **The rehearsal planner now rotates** across boards (`f2-pin-p1a`, `f3-blocked-p1a`, `f0-pin-p0a`, `f0-pin-p1a` in blocks 1-4) instead of retargeting one pair.
- **Cross-block retention is weak.** `f2-pin-p1a`'s correct move was rank 15/22 in block 1 and 11/22 in block 4. Receipts show task pulses with ReversalMemory factor D of about -1.0 and Stockfish pulses about -0.5; with eta 0.5, `dg = eta*D*(k+g-1)` halves every *inactive* cell's deviation from 1 on each pulse in its compartment, so a board's learning decays within a few unrelated lessons. Steady state is g = 1 - (fraction of pulses in which the cell was active), so one board among 24 can shift its cells by only about 1/24.
- **Dose proxy (training rows only; linear readout with heterogeneous base weights; crude planner; NOT the Fly):** no tested eta (0.5-0.02) learned the 24 boards (best 9-11/24 vs 7/24 untrained), and removing the recovery term did not fix it either. The proxy is too crude to choose a mechanism; it is recorded as a negative design probe only. The real revision-6 diagnosis (training boards at blocks 0 and 8 for every arm) is the evidence to wait for.
- Mechanism options are recorded for the next decision, not adopted: a smaller registered eta (dose); a separately registered rule variant; or the G0-tested `RateTimingMemory` receiver (8-association acquisition and interference retention in G0, single-channel, reversal failed).

### Smoke r6 official result (2026-10-24 13:15) and a second encoder flaw

Audit published (`runs/lichess-stage1-synthetic-v1-smoke-r6/audit.json`, full replay and memory continuity true); campaign stopped `gate-failed` (D2). `receiverAccepted` is no longer missing (policy B). Diagnosis line: validation at block 8: 3/16 (v1 input: 0/16); training boards (24): informative block 0: 4, block 8: 1; controls at block 8: outcome-only 5, absent 3, disabled 4, shuffled 3, stockfish-shuffled 7. Single replica, 24 boards: small differences are noise, but the taught arm did not learn and ended below the untouched baseline.

**Mistake (design, mine): Stockfish teaching is disconnected from move choice under the new cue.** `public-action-relative-cue-v1` gives child-position cues (`action:null`, used by the Stockfish value pulse) a separate `state:` token family. Measured on all 390 training moves (`state-action-overlap.mjs` in the diagnostics folder): the cue of the position after move X has 15.4 cells, of which only 2.63 are shared with move X's own cue (task token plus collisions). So the value channel trains cells the unaided ranking hardly reads, while each value pulse still triggers ReversalMemory's recovery term and erases task learning. This plausibly explains informative (outcome + Stockfish) ending below outcome-only. Under the v1 cue the child and action cues overlapped heavily by accident (shared board tokens). Implication for D9 and for the memory acceptance check: the value channel needs a representation in which the position after X and the choice of X share cells, with the delivered value sign expressed in the perspective of those shared cells (the mover's), or a recorded decision that Stockfish teaches position value for search only. Passed to the second model as a binding reviewer finding.
