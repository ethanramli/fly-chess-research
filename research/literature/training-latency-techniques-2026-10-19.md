## Exact data-copy opportunity

With N neurons, E edges, float32 storage and eight steps, the current accumulator copies **8E + 40N + 4 bytes per forward**: row offsets 4(N+1), columns 4E, signed weights 4E, drive 4N and eight previous states 32N. This counts payload bytes copied, not total memory-bus traffic or elapsed time. At the inspected N=134209, the neuron-dependent term alone is 5368364 bytes (about 5.12MiB); E must come from the pinned graph rather than a historical assumption.

Shared ownership is preferable to a cache that assumes weights stay unchanged: local plasticity, optimizer steps and checkpoint restoration legitimately update them. A candidate must demonstrate that all writers see the same buffers, that graph edits/error detection remain equivalent, and that no view can be detached by growth. Construction already uses initial=maximum pages; do not call grow, including grow(0). Do not replace teaching history with two rolling buffers: downstream trajectory evidence and derivatives consume the retained buffers.

The queued v3 profiler measures prepare as csrCopies; csrAccumulation includes both the previous-state copy and the kernel. It does not separately time the latter copy, so do not call the whole accumulation timer avoidable copying. Any refined instrumentation needs a new preserved registration, not an edit to the queued pinned version.

## Recovery and whole-process limits

An audit recovery candidate can prevent repeated completed work after interruption; it does not speed an uninterrupted neural forward pass. A good first boundary is stage-end, where no teaching session is pending. Exact replay from the checkpoint must reproduce an uninterrupted auditor and reject altered receipts, source identities, partial publications and checkpoint physiology. Resource waiting in the current auditor handles transient free-memory pressure; it does not provide interruption recovery.

The v3 comparison covers complete selected lessons across all six arms, not every whole-run phase. The original full audit has 15481 presentations: 12768 teaching frames, 1344 lesson assessments, 1152 stage-end/reset/restore assessments, 192 reversal-entry assessments, 24 baseline assessments and one initial reference. The 1369 presentations outside teaching lessons are about 8.84% of all presentations; this is a count share, not an elapsed-time share. Cold setup, stage boundaries, independent audit, interruptions and time to equivalent quality still belong in an eventual whole-training claim.

Pacing deliberately adds rest and is not a latency defect to remove. The existing callback excludes later checkpoint CPU. Retain duty0.5 and report process CPU/elapsed separately; changing pacing while comparing codecs would confound the measurement.

## Approaches not selected

- The [earlier zero-reset first-step candidate](../reports/move-latency-zero-reset-2026-10-10/README.md) passed equivalence but failed its latency gate. Its failed full-graph result remains authoritative; the idea is not a newly found successful optimization.
- SpMV search found [Xia et al.'s CPU performance model](https://doi.org/10.1109/TPDS.2022.3225230), but only its abstract was reviewed. It motivates measuring pipeline and memory effects; it supplies no measured bottleneck or expected gain for this laptop.
- GPU-specific overlap papers, workers, new sparse formats and SIMD reduction/reordering are not justified by this workload's measurements and exact-state requirements.
- SQLite is a design reference, not a proposed dependency. Its advertised database workload gains cannot be transferred to this checkpoint pipeline.

## Order of work

1. Let the existing audit finish, then run the already frozen v3 paired lessons and independent disk/timing audit in the authorized exclusive window.
2. Use the phase attribution to decide whether shared Wasm buffers justify a separate candidate; test exact histories, gradients, feedback, restore/update paths and both precisions before matched graph timing.
3. Register future audit recovery independently and prove interrupted/uninterrupted equality on a small archived fixture before any graph use.
4. Measure omitted full-run stages and recovery cost before describing any percentage as a whole-training improvement. No learning, transfer or biological gate follows from faster execution.


## 2026-10-19: Exa follow-up and the larger recomputation question

Three targeted Exa searches requested15 result entries across Wasm math calls, exact sparse computation and binary hashing. This counts result entries, not fully read papers. [Access and coverage](../reports/training-latency-2026-10-19/search-followup-access.json).

- Official [Node22 crypto source documentation](https://raw.githubusercontent.com/nodejs/node/v22.23.2/doc/api/crypto.md) explicitly accepts Buffer/TypedArray/DataView hash input and repeated updates. [Buffer documentation](https://nodejs.org/docs/latest-v22.x/api/buffer.html#static-method-bufferfromarraybuffer-byteoffset-length) describes shared views with exact offset/length. Potential adaptation: versioned binary neural-state evidence with dtype, length, endian convention and exact view span. This changes historical hash identity and must never be substituted into frozen receipts. No such change is implemented.
- Node26's pinned [recognized Wasm imports](https://raw.githubusercontent.com/nodejs/node/v26.12.0/deps/v8/src/wasm/well-known-imports.h) lacks Math.tanh in that list. Its [math header](https://raw.githubusercontent.com/nodejs/node/v26.12.0/deps/v8/src/base/ieee754.h) still declares tanh; a search-returned std::tanh change is not present in this release header. Do not assume a fused Wasm activation has free intrinsic calls or that another engine revision's optimization is installed. No local gain established.
- [SELL-C-sigma](https://arxiv.org/abs/1307.6209) coverage is abstract and metadata only. It supports investigating hardware-specific sparse layouts, not a particular gain, unchanged summation or applicability to this laptop. New graph layouts require original neuron mapping, unchanged per-row accumulation and measured memory justification.
- [ECMAScript JSON algorithms](https://tc39.es/ecma262/multipage/structured-data.html#sec-serializejsonproperty) describe finite-number conversion and compact ordered array serialization. Retrieved page labels itself a2027 draft; actual Node compatibility still needs exact-byte checks. A bounded per-position number-token cache might preserve old canonical JSON hashes if many values are identical across frames. This is our engineering hypothesis, not an external performance result. Earlier88-90% spatial uniqueness does not measure temporal reuse at the same neuron. Do not assume temporal stability or build this cache before checking it.

Researcher challenges the focus on small gains. The larger engineering question is whether the simulator needlessly recomputes whole-network rows whose initial values, incoming values, weights and drive are unchanged. An exact incremental engine would have to recompute every dirty row in the original edge order, preserve all retained histories and every released identity, and propagate changes without approximate thresholds or delta-sum rounding. Unchanged final frame values alone do not prove intermediate histories can be skipped. No incremental engine is implemented or assumed faster.

Next concrete evidence: analyze archived checkpoints across all24 stages and all6 arms, selecting first/middle/last lessons before looking at reuse. Count exact per-neuron and chunk stability between all19 frames, bind each state to its original receipt hash, preserve input hashes and resource guards. This observational analysis loads no graph and changes no learner. If reuse is substantial, separately measure intermediate dirty rows and the cost of preserving exactness before a new full-graph candidate. Preserve the current fresh-process benchmark unchanged and wait until its audit is terminal before local analysis.


## Exact incremental computation: primary-source follow-up

[Acar, Blume and Donham2011](https://arxiv.org/abs/1106.0478) describes consistent reuse with change propagation; coverage is abstract/metadata, not the full91-page proof. The [author-hosted Adapton paper](https://www.cs.umd.edu/~mwh/papers/adapton-submit.pdf) was inspected through its first14000 extracted characters, covering abstract/intro portions. Both motivate a correctness requirement: cached results must agree with recomputation after all relevant mutations are accounted for. They do not prove a FlyChess implementation correct or faster. [Access record](../reports/training-latency-2026-10-19/search-incremental-access.json); one search requested5 entries.

Adaptation limits: receipt hashing demands every final neuron value; learning and supervised comparison paths consume retained histories. Demand-driven omission of those outputs is therefore unavailable. Any incremental engine must preserve all outputs/histories and track changes in initial state, drive, weights, topology, activation parameters and restoration, with original per-row floating-point order. Derived caches must be disposable without changing learned behavior; they are engineering state, not a new learning mechanism. No library, dependency or engine is added.

Important comparison refinement before observing data: NeuralEpisode.begin resets the episode to zero every lesson. Adjacent frames can differ because their numerical time differs even when the same global startup work recurs across lessons. Final observational v3 therefore compares both adjacent frames and corresponding frame indices across the first/middle/last lessons in each stage, with public-input hashes and explicit dependency caveats. It also measures Float32 XOR-byte changes to distinguish numeric changes from temporal bit redundancy. Neither equality nor bit redundancy is a speed/compression result. The reference frame cache is bounded to one stage,19*N*4bytes=10199884bytes at134209 neurons, rather than storing all histories.


## 2026-10-19: Independent-row SIMD, source review before experiment

Primary [WebAssembly SIMD semantics](https://raw.githubusercontent.com/WebAssembly/simd/main/proposals/simd/SIMD.md) and [binary encoding](https://raw.githubusercontent.com/WebAssembly/simd/main/proposals/simd/BinarySIMD.md), accessed2026-10-19 via Exa, specify lane-wise scalar-compatible IEEE operations/roundTiesToEven, separate f64x2.mul/add, low-Float32-to-Float64 conversion and0xfd plus LEB128 opcode encoding. Target arithmetic/conversion/lane/load sections inspected. [Kreutzer et al., SELL-C-sigma](https://arxiv.org/pdf/1307.6209) coverage now extends earlier abstract-only review to extracted sections3.2-3.4: row chunks, padding, sorting and vectorization without horizontal reduction; figures not visually inspected. Access record: research/reports/training-latency-2026-10-19/search-row-simd-access.json.

Proposed adaptation: place independent original neuron rows in separate SIMD lanes, retaining every original edge order and separate f64 product/add. Preserve released identities through row mapping; use explicit padding masks to preserve signed zero and avoid adding artificial zeros. No relaxed SIMD, FMA, pruning or dropped histories. This is our exactness/engineering design; the sources do not prove its local equivalence or speed. Gather, padding, layout rebuilds/weight updates and extra memory must be measured under original guards. No implementation/test/adoption or local gain yet.
