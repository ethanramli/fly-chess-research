## 1. The fly got the same eye input for a capture and a non-capture

**Fix:** new input version, [Eyes v2](../../../documentation/design/chess-input/eyes-v2.md). It is Eyes v1 plus a dim picture (brightness 0.25) of the captured piece on the square it was removed from. New tests must use it. A new check, `inputCollisions`, must find zero items with identical input and different answers in every task set before use. Eyes v1 stays frozen for earlier runs.

**Evidence:** [eyes-v2.test.mjs](../../../.codebase/tests/chess-input/eyes-v2.test.mjs) passes 7 of 7. On the real retina map, the review's two positions give identical Eyes v1 input and different Eyes v2 input; the collision check finds one conflicting group under Eyes v1 and none under Eyes v2. Moves that do not capture give exactly the Eyes v1 input.

**Limit:** Eyes v2 still omits castling rights, en-passant rights and move history. The safe-capture answer does not depend on them (argument in the revision, problem 1). Later tasks must pass the collision check.

## 4. The pilot changed the fly's memory between move scores

**Fix:** a decision and a check. Every future move chooser must score all proposed moves from one unchanged stored memory, and learn only after the choice. `frozenScores` in [transfer-evaluation-v1.mjs](../../../.codebase/src/neural-learning/transfer-evaluation-v1.mjs) checks the complete memory fingerprint after each score, scores the moves again in reversed order, and stops with an error if memory changed or order changed a score. The audit must repeat the reversed-order check.

**Evidence:** [transfer-evaluation-v1.test.mjs](../../../.codebase/tests/neural-learning/transfer-evaluation-v1.test.mjs) passes 15 of 15, including a scorer that changes memory and a scorer whose result depends on order; both are rejected.

**Preserved:** the completed pilot is not rerun. Its practice choices are now labeled "scored while memory changed" in a dated correction at the top of the [pilot report](../long-term-memory-v1-live-comparison-2026-11-01/README.md); its read-only tests are unaffected. The future chooser does not exist yet; this rule binds it.

## 5. The eye test used an unreachable strength, and the move score was incomplete

**Fix:** the original eye test (restart plan section 7) is preserved and recorded as blocked, because no inspected rule reaches 1.8. **Eye test v2** replaces it for future use, using the earlier written proposal (option A of the [eLife protocol](../../../documentation/design/research-goals/elife-prospective-protocol-2026-11-02.md)): strengths 0.2 and 1.0 only, chosen by decoder sign; an exact strength measure M that needs no approach or avoid labels; the same 10% threshold and every original count rule. The training move score is now fully stated: MBON05 with coefficient −1, the other four types 0, a fixed choice temperature rule, move order, random seed and error rule.

**Implemented:** the score uses the existing `scoreNeurons` with a new coefficient contract, [move-score-contract-v1.json](../../../.codebase/src/neural-learning/move-score-contract-v1.json) (MBON05 at −1 with its source and both pinned MBON05 cells; the other four types at 0). The choice over all legal moves is [move-chooser-v1.mjs](../../../.codebase/src/neural-learning/move-chooser-v1.mjs): moves in sorted order, every score taken with `frozenScores`, choice probability proportional to exp(score / T), T = 0.1 × the spread of MBON05 activity, and a fixed seed rule. Tests: [move-chooser-v1.test.mjs](../../../.codebase/tests/neural-learning/move-chooser-v1.test.mjs) passes 6 of 6 and [move-score-contract-v1.test.mjs](../../../.codebase/tests/neural-learning/move-score-contract-v1.test.mjs) passes 2 of 2.

**Eye test v2 in code:** [eye-test-v2.mjs](../../../.codebase/src/neural-learning/eye-test-v2.mjs) computes the reachable strength settings (never above 1.0), the strength measure M and the 10% gate. Its test, [eye-test-v2.test.mjs](../../../.codebase/tests/neural-learning/eye-test-v2.test.mjs), passes 4 of 4.

**Status: resolved.** The review asked for reachable strengths and an exact score rule before the eye test runs ("First approve reachable strengths and an exact score rule"). Both are decided, written down and built.

**Prerequisite for training, outside this finding:** the contract is marked "awaiting-memory-compatibility", so `scoreNeurons` refuses it. This switch-on rule was already part of the approved plan (section 4A point 2) before the review. MBON05 may be used for training only after the separately approved memory test on the brain model shows that feedback moves its margins both ways against controls. This work was not allowed to run that test. When it passes, the run fills in the contract and the chooser works without any code change.

## 6. The planned en-passant test group could not occur

**Fix:** the group is replaced by "the fly captures en passant; the opponent may recapture the capturing pawn with an ordinary capture". The count stays at 6 pairs. Examples must come from real game history. The safe-capture checker is unchanged, because it checks the landing square, which is correct for this group.

**Evidence:** [en-passant-capture-group.test.mjs](../../../.codebase/tests/search-and-feedback/en-passant-capture-group.test.mjs) passes 5 of 5. It builds both twins from real moves, confirms the safe and unsafe answers, and finds no en-passant reply after any of 266 sampled captures.

## 7. The separate answer file only gives exact matches

**Fix:** the answer file is excluded from every transfer and combination claim and becomes a comparison system (the exact-recall store). `exactRepeats` must find zero test inputs identical to training inputs. A new comparison system, similar-board recall (`similarBoardRecall`), answers a new board by its most similar trained input; the fly must beat it, so a transfer result cannot be explained by input similarity alone. The plan now states where learning on a new board must come from: changes in KC-to-output connection strengths made by the approved memory rule.

**Evidence:** the same transfer-evaluation tests cover exact-repeat detection (a 0.000001 change is not a repeat) and similar-board recall.

**Status: resolved.** The review asked to "specify how training changes the fly's stored brain values and compare it with fair alternatives". The revision names where the lasting change must be and what drives it, and both new comparison systems are built and tested.

**Correction (later on 2026-11-03):** the first version of this fix also required transfer to come only from changes inside the brain. That contradicted the researcher's 2026-11-01 permission for disclosed engineered memory and is corrected in the revision (problem 7 correction): each test declares brain-only or engineered memory, and results are reported for that system. The reasoning-first scope is unchanged.

**Prerequisite for running, outside this finding:** the exact memory equation is the plan's section 5 decision. It was open before the review and needs the researcher's approval after the memory test. No transfer test can start before that.

## 8. The later transfer and combination tests were incomplete

**Fix:** the [transfer and combination protocol](../../../documentation/design/research-goals/transfer-and-combination-protocol-2026-11-03.md) gives exact tasks, comparison systems, practice budgets, pass scores and stopping rules for Phase B (transfer) and Phase C (combination). Phase C has two steps: two ideas, then three ideas, because two is not "many". Each test pair changes the condition of exactly one idea, so a system missing that idea fails that pair; this is how each idea is shown to be needed. All untaught combinations are listed. A fixed-sum combiner arm tests whether a fixed addition of separate scores explains the result. The pass rule is implemented as `pairGate`.

**Answer checker in code:** [landing-square-certificate.mjs](../../../.codebase/src/search-and-feedback/landing-square-certificate.mjs) certifies every Phase B and Phase C answer. For any legal non-king move it lists every legal opponent capture of the moved piece, the pinned attackers and the exchange values, and `combinedAnswer` applies the combined rule. Its test, [landing-square-certificate.test.mjs](../../../.codebase/tests/search-and-feedback/landing-square-certificate.test.mjs), passes 9 of 9, including a pinned-attacker twin pair and both exchange-value cases.

**Status: resolved.** The review asked for exact problems, comparison systems, required scores, stopping rules, why each idea is needed, and the untaught combinations. All are written, the pass rule is built (`pairGate`) and the answer checker is built.

**Twin-pair generator in code:** [twin-pair-generator-v1.mjs](../../../.codebase/src/puzzle-learning/twin-pair-generator-v1.mjs) applies the old and new game splits, replays real game histories, makes one-edit twins and rejects any pair whose edit changes more than one idea, whose answers match, or whose eye inputs collide. [twin-pair-search-v1.mjs](../../../.codebase/src/puzzle-learning/twin-pair-search-v1.mjs) tries every single-square edit, and [generate-twin-pairs.mjs](../../../.codebase/scripts/data/generate-twin-pairs.mjs) runs it on a PGN file for the train or development bucket only; it refuses locked buckets. Tests: 9 of 9 and 4 of 4. It has not run on real data.

**Needs approval:** the game source and split (Proposal C in the [approval proposals](../../../documentation/design/research-goals/approval-proposals-2026-11-03.md)). Phases B and C also cannot start before Phase A passes.

## Exact constraints that stop the later runs

Each constraint below now has a concrete proposal in the [approval proposals](../../../documentation/design/research-goals/approval-proposals-2026-11-03.md).

Every finding above has its fix in code, in the plan, or both. These four items stop later *runs*, not the fixes. Each is a project rule or a missing input, and this work was not allowed to remove it.

1. **MBON05 for training (problem 5).** Prevented by: the approved plan (section 4A point 2) allows a nonzero coefficient only after a memory test on the brain model, and this goal forbids brain-model experiments. What unblocks it: run the separately approved memory test; if it passes, fill in the contract's identities and evidence codes.
2. **The memory equation (problems 7 and 8).** Prevented by: the plan (section 5) says the rule is chosen only after the eye test passes and only with the researcher's approval. The eye test is a brain-model run. What unblocks it: run Eye test v2, then the researcher approves a rule.
3. **Twin-pair data for every phase (problems 6 and 8).** The generator is built and tested. Prevented by: no restart game source is registered, and choosing one is the researcher's data decision (Proposal C). What unblocks it: approve Proposal C; then build the old-training code list, fetch histories and run the generator on the train and development buckets. Locked sets need a further sealed-generation approval.
4. **The fixture-replay test (`pipeline-lesson-fixture.test.mjs`).** Prevented by: it replays checkpoints of the preserved local run `runs/g0-history-fixture-v1-uninterrupted`, which is not in git and no longer holds `checkpoint-000005.json.gz`. Writing new checkpoints into that preserved run folder would change evidence. What unblocks it: regenerate the fixture run into a new folder and point the test at it, with the researcher's agreement.
